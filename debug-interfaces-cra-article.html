1. The Central Thesis: Controlled Access, Not Blanket Disablement

One of the most persistent and unproductive debates in embedded product security reviews is whether every UART, JTAG, SWD, or serial debug interface must be permanently disabled before a product ships.

The security team's instinct — reduce the attack surface — is correct in direction but often imprecise in prescription. Telling engineering "disable all debug ports" conflates four fundamentally different things: diagnostic log output, interactive console access, bootloader shells, and hardware debug access. Each presents a different threat and allows different levels of operational flexibility.

Core principle: CRA and RED-DA require security outcomes. They do not prescribe that every UART, JTAG, SWD, or debug interface must be physically removed or permanently blocked. The right question is not "is this port open or closed?" but "is access to this interface appropriately controlled, authenticated, monitored, and proportionate to the risk it presents?"

Figure 1 — The three objectives are not competing. A mature product security architecture delivers all three simultaneously.

3. What the Law Actually Says — CRA and RED-DA

3.1 CRA Annex I, Part I — Six Clauses That Matter

CRA RefRequirementRelevance to Debug Interfaces
§1(a)"Appropriate cybersecurity level based on the risks"Risk-based, not prescriptive. A port is not inherently non-compliant; its uncontrolled access is.
§1(b)"Delivered without any known exploitable vulnerabilities"Open U-Boot shell with bootdelay=5 is a known, exploitable vulnerability. No argument survives this clause.
§1(d)"Protect the confidentiality of stored, transmitted or processed data"Logs emitting runtime state, kernel versions, tokens trigger this obligation.
§1(e)"Protect the integrity of data, commands, software and configuration"A writable serial console or U-Boot shell allows unsigned firmware injection.
§1(g)"Minimise their own attack surface, including external interfaces"The word is minimise, not eliminate. Authenticated, logged debug access has a minimised attack surface.
§1(i)"Record and monitor relevant internal activity"A logging obligation — but serial is not mandated as the channel.

3.2 SHOULD vs SHALL — The Most Important Normative Distinction

ETSI EN 303 645 Clause 5.6 uses SHOULD throughout its debug interface provisions. EN 18031-1:2024 upgrades the obligation to SHALL for interfaces providing privileged access to system resources (bootloader console, root shell, unauthenticated JTAG).

The most consequential mistake in product security reviews is treating every debug interface as equivalent. The diagram below maps the capability spectrum to realistic threat levels.

5. Real-World Reconnaissance: Six Cases Mapped to Threat Categories

The claim that serial logs "contain no sensitive information" is frequently used to justify leaving interfaces open. The following cases demonstrate how serial output has enabled real-world attack chains. Not every case has a CVE — but that is not because they are configuration or design issues. The CVE Program explicitly accepts configuration weaknesses (CWE-16), insecure defaults (CWE-1188), and missing authentication flaws (CWE-306) as eligible vulnerability types. The reason specific cases here lack CVEs varies: some were resolved through responsible disclosure without a CVE being filed; some are conceptual/research demonstrations without a single named-product scope required for assignment; and some simply were not submitted through the CVE request process. Absence of a CVE does not diminish the exploitability — it reflects a process gap, not a risk gap.

Figure 5 — Six real-world cases mapped to threat categories, CRA clauses, and CVE status. All six cases are real and documented; not all have CVE identifiers because CVEs apply to specific software flaws, not design/configuration exposures.

On CVEs and configuration / design vulnerabilities: A common misconception is that CVEs only cover code bugs. This is incorrect. The CVE Program (MITRE / NVD) explicitly accepts vulnerability reports for configuration weaknesses, insecure defaults, and architectural design flaws — provided they are exploitable, independently fixable, and affect a specific named product. Relevant CWE categories that map directly to this article include: CWE-1188 (Insecure Default Initialization of Resource — e.g., bootdelay=5), CWE-306 (Missing Authentication for Critical Function — e.g., open UART root shell), CWE-284 (Improper Access Control — e.g., unauthenticated JTAG), and CWE-16 (Configuration). The cases in this article that lack CVEs are missing them for practical reasons: (a) the researcher or vendor chose responsible disclosure without requesting a CVE assignment; (b) the finding was a conceptual research demonstration not tied to a single named product version; or (c) the CVE request was simply never submitted. None of these cases lack CVEs because they are configuration or design issues — that rationale is factually wrong and should not be used to downplay their severity.

7. Fifteen Engineering Pushbacks — With Authoritative Responses

Pushback 1: "We need logs to know things are going right"

Operationally valid. CRA §1(i) actually creates a monitoring obligation. The debate is not about whether to log — it is about where logs go and who can access them. Compliant alternatives: remote authenticated syslog to a TLS-secured cloud endpoint (your cloud management platform likely already has this infrastructure), persistent circular log in /var/log/ pulled via authenticated SSH or HTTPS API, or structured application logs pushed to a secure backend on reconnect. The serial port is a development-time convenience that became a production habit.

Pushback 2: "Serial log messages don't contain PII or sensitive info"

Factually incomplete. CRA §1(g) attack surface minimization is not limited to PII. The question under CRA is not "does it contain PII?" but "does it increase exploitability?" Even sanitised logs typically reveal: kernel version (enabling CVE lookup), software versions, service names, network endpoints, authentication events, and filesystem topology. Additionally, energy behavioral patterns emitted on serial are personal data under GDPR Art.4(1) regardless of whether they contain a name. See Case 6 above.

Pushback 3: "If we disable serial, we need a different firmware image for diagnosis"

Valid concern, wrong conclusion. Maintaining a separate debug firmware image creates more risk: separate signing, potential for the debug image to end up in production, and no guarantee it reflects the actual production state. The correct architecture is one signed production binary with security-controlled diagnostic modes — same image, different authenticated configuration. The debug capability exists in the binary; production configuration simply does not activate it without authentication. See Section 10.

Pushback 4: "What about a configuration parameter to enable/disable the serial port?"

Good direction — with strict conditions. A configuration parameter is not inherently a security control. If a filesystem-accessible file enables the port, an attacker with any system access can flip it. A compliant implementation requires: disabled state is factory default, enabling requires a signed token or authenticated API call, the config partition is write-protected, enabling events are logged to a remote audit log, and the port auto-disables after a timeout or reboot.

Pushback 5: "What if serial communication is encrypted with per-device unique keys, decryptable only by the RMA server?"

Strong for the application log stream. Insufficient by itself. Encryption addresses CRA §1(d). What it does not address: (a) U-Boot is pre-kernel — encryption is not running during the bootloader window, which is where this exact class of bootloader attack occurred on a production device. (b) Duplex serial with encryption still allows MitM command injection if the channel is bidirectional. (c) Server-side key compromise radius covers the entire fleet. Verdict: implement encrypted per-device log streams for the application layer, pair it with simplex UART (TX only), and harden the bootloader separately. These are complementary, not alternative, controls.

Pushback 6: "Energy telemetry is not sensitive — an attacker can't use energy data"

Factually incorrect. See Case 6. Occupancy inference from daily energy patterns is a documented behavioral profiling attack. Under GDPR Art.4(1), behavioral patterns from which a person's occupancy can be inferred at a named address are personal data. RED-DA Art.3(3)(e) mandates protection of such data. The correct response is not to stop collecting the telemetry — it is to route it through an authenticated, encrypted cloud channel instead of broadcasting it on an unauthenticated physical interface.

Pushback 7: "What if the serial interface is simplex — output only, the device never reads from it?"

Meaningful risk reduction. Acceptable as part of layered controls. Insufficient alone. Simplex eliminates command injection and configuration manipulation at the kernel/application level — a genuine improvement. What it does not eliminate: information disclosure (Cases 1, 3, 6 still apply), and the U-Boot attack window (which occurs before Linux loads, where your simplex setting has no effect). Simplex UART TX with kernel log suppressed and application log filtered is a defensible Tier 3 configuration with documented residual risk.

Pushback 8: "The serial console only shows Linux kernel boot messages — that's the kernel printing them, not our application code"

Factually correct observation — but the wrong conclusion follows from it. The developer is right on the technical fact: printk is a Linux kernel subsystem, not an application-layer logging call. It is the kernel itself that prints boot progress, driver initialization, hardware probing, and runtime events directly to the serial console — none of this is written by the product's application team. It is completely separate from any printf, syslog, or custom logging framework in your business application.

However, this distinction does not reduce the security risk — it actually makes the exposure harder to miss in a code review, because the kernel emits these messages regardless of what the application does. By default, every Linux boot sequence announces itself over serial with messages like:

  • Linux version 5.4.3 (gcc 8.3.0, Buildroot 2019.02) — exact kernel and toolchain version → automated CVE lookup in seconds
  • EXT4-fs (mmcblk0p3): mounted filesystem — partition layout and filesystem type
  • Starting systemd version 249.11 — init system version → known vulnerability surface
  • Started OpenSSH server daemon — confirms which network services are running

None of that is your application's log. All of it is the kernel's own self-description, and all of it is reconnaissance gold for an attacker with a $4 USB-serial cable. The product team is responsible for how the kernel is configured — this is a Board Support Package (BSP) setting, not application code. The fix is a single line in the kernel bootargs, not a code change: quiet loglevel=0 console=null. The kernel continues to maintain its full internal log ring buffer; all messages remain accessible via dmesg and journalctl over an authenticated session. Zero engineering effort. Zero loss of diagnostic capability.

Pushback 9: "Our device is physically enclosed — the serial port is not accessible"

Physical enclosure is not a security control under CRA. CRA Article 13 risk assessment must consider "reasonably foreseeable use" over the product's lifetime. Solar gateways are installed on exterior walls, in utility rooms, and in publicly accessible buildings. A motivated attacker can open a plastic enclosure in under 60 seconds. If UART headers or test pads are accessible after opening, the interface is in scope. Acceptable physical controls include removed/potted test pads, conformal coating over headers, and a register-level hardware disable of the UART peripheral.

Pushback 10: "We already have secure boot — serial can't be used to load bad firmware"

Secure boot and an open serial console are orthogonal controls. Secure boot validates boot stage integrity before execution. It does not prevent: U-Boot environment variable manipulation that redirects the boot path without replacing the image; memory extraction via U-Boot md commands that dumps keys, certificates, and secrets from RAM; or serial console root shell access that modifies the running system without touching the boot path. Secure boot is critical. It is not a substitute for bootloader console hardening.

Pushback 11: "The serial port is only used during factory testing — it's left on by accident"

CRA applies to shipped products, not intended configurations. CRA §1(b) applies to the product as delivered. If the serial console is active in the firmware image that ships, the fact that it was "only intended for factory use" is legally irrelevant. This is an argument for integrating security configuration into the CI/CD build pipeline — a build-time gate that fails the production image signing if factory debug settings are present — not for leaving the port open.

Pushback 12: "There's no external connector — the UART is on an internal header with no cable"

Partial risk reduction. Not sufficient under EN 18031-1. EN 18031-1 ACM-5 applies to any interface "accessible in a production device." Accessibility is not limited to externally connected interfaces. A UART with a populated PCB header or exposed test pads is accessible with a Dupont cable or test clips after the enclosure is opened. Missing connector ≠ disabled interface. The assessment must address whether the interface can be reached after enclosure opening, which for a fixed-installation energy gateway is a realistic scenario.

Pushback 13: "We'll document it as a known risk and accept it"

Risk acceptance is a valid process step — not a compliance workaround. CRA §1(b) requires that products are delivered "without any known exploitable vulnerabilities." Risk acceptance cannot override this. It applies to residual risks after controls are applied, to risks that cannot be reasonably mitigated, or to SHOULD-level deviations. It is not applicable to SHALL-level requirements or the §1(b) baseline. Attempting to CE-mark a product with an unmitigated known vulnerability by citing risk acceptance documentation is a compliance failure.

Pushback 14: "Our product is B2B — RED-DA only applies to consumer products"

Incorrect interpretation of scope. RED-DA Commission Delegated Regulation (EU) 2022/30 applies to specified categories of radio equipment based on technical characteristics, not customer segment. If your gateway connects to the internet and falls within the specified product categories, RED-DA applies regardless of whether it is sold to homeowners, installers, or commercial operators. CRA scope is similarly based on "products with digital elements" — which includes commercial and industrial IoT products.

Pushback 15: "We use RS-485 / Modbus RTU for communicating with solar panels, meters, and battery systems — you can't disable that serial interface"

Legitimate and important distinction. RS-485/Modbus RTU is a field bus, not a debug console — they require different security treatments. This pushback correctly identifies that "disable all UART" is an oversimplification. A renewable energy gateway may use:

  • UART0 — Debug console (this is what should be hardened/disabled)
  • UART1 or RS-485 controller — Modbus RTU to microinverters, energy meters, or battery management systems (this must remain functional)

These are physically different interfaces and software channels. The security treatment for Modbus RTU is distinct: Modbus RTU (IEC 61158) has no built-in authentication. Mitigations include: physical isolation of the RS-485 bus, Modbus firewall/gateway (MOXA MB3000 class), data integrity at the application layer (CRC validation is native to Modbus), and referencing IEC 62351-5 for authenticated Modbus extensions. The debug console and the Modbus field bus are separate concerns — do not let conflation of the two become a reason to leave the debug console open.

8. The FST Troubleshooting Scenario — The Hardest Pushback

Scenario: A device is deployed at a customer's premises. It stops functioning. The customer calls support. Level 1 escalates to Level 2. Level 2 escalates to device engineering. Engineering says: "I need serial access to understand what's happening — I cannot diagnose a production device without loading a debug-enabled image, and that's a different firmware, which may not reflect the production state."

This is the most operationally legitimate concern in the list. It deserves a real engineering answer, not a dismissal. The key insight is that this argument is used to justify open serial on all field devices when in reality it only applies to a specific failure scenario — and for the worst cases, serial doesn't help anyway.

Figure 7 — FST troubleshooting decision tree. Open serial on all field devices is not justified by the edge case that only applies to the middle failure class.

The recommended architecture for FST support:

  • pstore — persistent kernel crash logs written to a dedicated eMMC partition, surviving reboots. FST extracts via authenticated HTTPS API after any partial boot.
  • Cloud-triggered verbose logging — if the device has any network connectivity, the cloud support portal can push a signed configuration change that enables debug-level logging routed to the secure remote syslog endpoint.
  • Authenticated local diagnostic API — FST connects on the local LAN and uses a time-limited token (generated by the backend after engineer authentication) to pull diagnostic bundles via HTTPS.
  • Authenticated serial console — for genuine early-boot failures where network is unavailable, the authenticated serial console (Section 10) allows engineering access without leaving the port permanently open.
  • RMA for complete no-boot — this is correct and cannot be avoided. A device that cannot boot cannot be fixed in the field regardless of serial availability.

9. NXP i.MX 93 Crypto-JTAG and EdgeLock DAT

⚠️ RMA USE ONLY — Not Applicable to Field-Deployed Devices

The capability described in this section applies exclusively to devices that have been physically returned to an authorised service facility. It is not a mechanism for enabling JTAG access on devices deployed at customer premises. It requires: physical JTAG connection (not over serial or network), an OEM-held private key that never leaves the HSM, and a chip lifecycle fuse state that is irreversible once set. Field devices in OEM_CLOSED state cannot be JTAG-accessed without the full DAT protocol — this is by design and is the correct production security posture.

9.1 EdgeLock Secure Enclave (ELE) Overview

The NXP i.MX 93 integrates the EdgeLock Secure Enclave — an independent Arm Cortex-M33 security processor that operates separately from the application cores. It manages: secure boot and image authentication, Debug Authentication (JTAG access via PKI challenge-response), cryptographic key lifecycle, chip lifecycle fuse management, and an event log of all security-relevant actions. The ELE cannot be bypassed through software running on the application cores.

9.2 Chip Lifecycle Fuse States

Figure 8 — NXP i.MX 93 chip lifecycle fuse states. Fuse writes are one-way and irreversible. OEM_CLOSED must be burned at manufacturing end-of-line.

9.3 Debug Authentication Protocol (DAT) — How It Works

When a JTAG probe connects to an OEM_CLOSED device, the ELE executes an asymmetric challenge-response:

  1. JTAG probe connects. ELE generates a fresh nonce (challenge).
  2. The probe host must present a Debug Credential (DC) — an X.509-like certificate signed by the OEM Root Key — containing: device UUID scope, permitted debug access (which cores, which peripherals), and optional expiry timestamp.
  3. The probe host signs the challenge nonce with the DC private key.
  4. ELE verifies the signature chain: OEM Root Key → Debug Credential → challenge response. If valid, debug access is granted within the scope defined in the DC.
  5. ELE event log records the debug session (timestamp, DC hash, cores unlocked).
  6. When the probe disconnects, debug access is revoked. Session is logged as closed.
Key security properties satisfied: Authentication (OEM private key never leaves HSM), Authorization (scope is encoded in the DC), Audit (ELE event log), Non-repudiation (DC can be device-specific by UUID), Time limitation (DC can carry an expiry timestamp), Physical requirement (physical JTAG connection required — cannot be triggered remotely), Field protection (OEM_CLOSED state makes this impossible to perform in the field without the OEM credential).

10. Implementing an Authenticated Serial Console — High-Level Architecture

The architectural conclusion from all preceding sections is clear: an open, unauthenticated serial console is not compliant. But the operational need for serial-based diagnostics in specific scenarios is legitimate. This section provides high-level design approaches — the goal is to give architects the concept; implementation detail will vary by platform and security maturity level.

10.1 Embedded Linux — Three Architectural Approaches

Approach A — HMAC Challenge-Response Daemon (Recommended)

Concept: A minimal daemon starts early in the boot sequence, before the standard login shell. It emits a random 128-bit nonce over UART TX, then waits a fixed time window for a response. The correct response is HMAC-SHA256(device-unique-secret, nonce). If valid, it transitions the UART to an authenticated, time-limited login session. If no valid response arrives, UART RX is redirected to /dev/null.

Key design properties:

  • Device-unique secret stored in secure storage (TPM NVRAM, OP-TEE secure world, or at minimum a dm-verity-protected read-only partition)
  • Backend engineer tool queries an internal secrets vault (HSM) to generate the response — the secret never leaves the vault
  • Session timeout enforced (e.g., 60 minutes or N reboots)
  • All authentication events logged to remote syslog
  • Failed attempts increment a lockout counter

Availability: Operational from early userspace — captures post-kernel, pre-application failures.

Approach B — SSH Over Serial

Concept: A serial-to-socket bridge (e.g., ser2net) exposes the serial port as a local TCP socket. A lightweight SSH server (dropbear) listens on that socket. The FST or engineer connects via SSH over a USB-to-serial adapter, using device-specific Ed25519 keys provisioned at manufacturing.

Key design properties:

  • Leverages mature, battle-tested SSH authentication infrastructure
  • Key-based auth — no passwords to brute-force
  • Standard SSH audit logging
  • Can use certificate authority for fleet-wide key management

Limitation: Not available during early boot (kernel must be running and SSH server started). Suitable for application-layer diagnosis, not bootloader or kernel crash diagnosis.

Approach C — Time-Limited OTP Token

Concept: The serial console requires a TOTP (Time-based One-Time Password) derived from the device serial number. The backend generates the OTP after the engineer authenticates to the support portal. The device validates it against the same TOTP algorithm using the device seed stored in secure storage. Valid window is 30 seconds.

Key design properties:

  • Two-factor: device TOTP seed + engineer's backend authentication
  • Offline-capable: no network required at the device during authentication
  • Automatically expires — no persistent session risk

Consideration: Requires accurate clock on device (NTP or RTC). Time drift can cause false failures.

Approach D — Signed Debug Activation Token (OTA)

Concept: The production image contains the debug capability but it is off by default. A signed JSON Web Token (JWT) or CBOR-encoded token, issued by the product security team's backend and signed with the OEM private key, can be passed to the device via the authenticated HTTPS management API. The device verifies the signature, checks the token scope and expiry, and activates the debug console for the authorized window.

Key design properties:

  • Requires no physical serial access to authorize — works remotely
  • Token is device-scoped (device serial number embedded in JWT claims)
  • Token carries expiry and permission scope (log-only vs interactive shell)
  • Requires network connectivity to deliver the token

Best suited for: Remotely enabling verbose logging for degraded-but-networked devices — the most common FST scenario.

10.2 MCUboot + Zephyr RTOS — Two Approaches

MCUboot — GPIO-Gated Serial DFU

Concept: MCUboot's serial recovery DFU interface is disabled by default (CONFIG_MCUBOOT_SERIAL=n). For factory use, it can be activated only when a specific GPIO pin is held low during power-on — a pin that is physically inaccessible on the sealed production unit (e.g., under potted conformal coating on the manufacturing test jig connector). MCUboot always enforces image signature verification, even in serial recovery mode — only OEM-signed images are accepted.

Key design properties:

  • No serial recovery in normal operation
  • Factory: GPIO pin accessible on test jig, not in customer housing
  • Image authentication enforced regardless of recovery path
  • Time-limited DFU window configured via CONFIG_BOOT_SERIAL_WAIT_FOR_DFU

Zephyr Shell — Authenticated Module with Default-Off

Concept: The Zephyr Shell backend for UART (CONFIG_SHELL_BACKEND_SERIAL) is disabled in production. Logging is retained via the UART log backend in TX-only mode at WARNING level. For authenticated field access, a custom shell module can be built into the image that starts the shell in a locked state — only the auth command is available. After successful HMAC validation, the full command set unlocks for a timed session. Zephyr's logging framework continues to emit structured logs over UART TX independently of shell state.

Key design properties:

  • Logging and interactive shell are independent subsystems
  • Production: logging at WARNING level, shell locked
  • Authorized session: shell unlocked for 60 minutes, auto-reverts
  • MCUboot image signature always enforced

11. Adequate Security: What Is Minimally Required and the SSDL Phased Roadmap

11.1 What "Adequate Security" Means in CRA

CRA Article 6 and Recital 34 ground the entire regulation in proportionality: manufacturers must implement "an appropriate level of cybersecurity based on the risks." This is not absolute security (which is impossible) and not checkbox compliance (which provides no real protection). It is security that is proportionate to:

  • Threat likelihood: Is physical access to this device realistically achievable?
  • Impact severity: If compromised, what is the blast radius — one device, the fleet, or critical grid infrastructure?
  • Asset value: Does this device control physical energy flows, process financial data, store personal data?
  • Deployment lifetime: A solar installation has a 15–25 year lifecycle. Threats in year 15 will differ from threats at launch.
  • Deployment environment: A gateway in a locked IT room has a different physical threat model than one on a customer's exterior wall.

"Adequate" security for a debug interface means: the controls in place are proportionate to the realistic threat, documented, verifiable, and maintainable over the product's lifetime. It is not a destination — it is a defensible, evidence-backed position that must be re-evaluated at each major release.

14. Better Requirement Language

What Not to Write

"All UART, JTAG, and debugging interfaces shall be disabled in production."

This is unenforceable (what does "disabled" mean for a UART TX-only log path?), creates adversarial engineering relationships, and fails a compliance audit because it doesn't map to a verifiable security outcome.

What to Write Instead

"All debugging, diagnostic, and manufacturing interfaces shall be assessed for their potential to expose sensitive information, enable unauthorised access, modify product functionality, or compromise system availability. Interfaces providing privileged access to system resources (bootloader console, root shell, unauthenticated JTAG) shall be disabled or hardware-locked in production configurations. Interfaces required for legitimate diagnostic, maintenance, or recovery operations shall implement authentication, authorisation, time-limiting, and audit logging proportionate to the risk they present. Production configurations shall enforce secure defaults for all interfaces; enabling any diagnostic access shall be appropriately restricted, documented, and reversible. All interface security controls shall be verified by automated CI checks and periodic penetration testing."

This language gives engineering implementation flexibility, defines verifiable security outcomes, maps directly to CRA Annex I §1(b)(d)(e)(g)(i) and EN 18031-1 ACM-5, and survives a notified body assessment.

16. Conclusion

The debate between security teams and engineering teams over debug and serial interfaces is not a disagreement about values — both sides want the product to work reliably and securely. It is a disagreement about implementation specifics that stems from an imprecise framing of what the regulation actually requires.

CRA and RED-DA require security outcomes: minimised attack surfaces, no known exploitable vulnerabilities, protected confidentiality and integrity, authenticated access to privileged interfaces. They do not require the elimination of diagnostic capability. What they prohibit is the casual, unauthenticated exposure of privileged system access — which is exactly what an open U-Boot console, a root serial shell, and an unauthenticated JTAG port represent.

The question should not be: "Should we disable UART and JTAG?"

The question should be: "How do we ensure that diagnostic and debugging capabilities cannot be abused by unauthorised entities while remaining available to authorised personnel when operationally necessary — and how do we document and verify that?"

That is the difference between disabling functionality and engineering a secure product. Security, usability, and operability are not competing objectives. A mature product security architecture delivers all three.
